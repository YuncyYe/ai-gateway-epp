# TC-02 恢复后追平

| 项 | 内容 |
|---|---|
| 用例编号 / 名称 | TC-02 / 恢复后追平 |
| 所属场景 | SC04 InnerAPI 故障 fail-static |
| 版本 | v0.1 |

## 测试目的

验证故障窗口内向 mock 下发的配置变更不会在故障期间生效，也不会丢失：InnerAPI 恢复后 epp 自动拉到 pending 的 v2 配置并完成引擎换入（`ai_epp_engine_current_version` 哈希由 v1 变为 v2），调度恢复正常。

## 运行模式

单组件进程组：epp（真实进程）×1 + inference-sim（真实进程）×1 + ai-gateway-api mock + BFE 由测试代码扮演。每 TC 独立一套进程组与 mock。

## 前置条件

1. harness 已构建 epp 二进制；inference-sim 二进制可用（见总体说明 §2，缺失时 `t.Skip`）。
2. mock API 已配置 assignment 全量视图（cluster-a → 本实例 primary）、epp_config（cluster-a 最小配置）、cluster_table（1 个 sim 后端 a0）；epp 启动并就绪，已首拉成功。
3. 环境 ID `epp-sc04-tc02`，全部监听 `127.0.0.1` 动态端口。

## 测试步骤

| # | 操作 | 预期 |
|---|---|---|
| 1 | 拉取 epp metrics，记录 `ai_epp_engine_current_version{cluster="cluster-a"}` 当前值为 v1（哈希非空） | v1 存在且非空；为空则用例失败 |
| 2 | `SetFail(true)` 进入故障态，随即 `SetEppConfig` 对 cluster-a 下发 v2 epp_config：在最小配置基础上将插件键 `"max-score"` 重命名为 `"max-score-v2"`（内容变化，哈希必变） | mock 已保存 v2 配置，但 epp 拉取失败 |
| 3 | 再次读取 `ai_epp_engine_current_version{cluster="cluster-a"}` | 仍为 v1：故障期间 pending 配置不影响在服务的引擎（fail-static） |
| 4 | `SetFail(false)` 恢复 InnerAPI，以 `WaitFor`（20s 超时）轮询版本指标 | 哈希变为 v2，pending 配置在恢复后自动追平生效 |
| 5 | 发送 ext-proc pick：`llm-d.ai/inference-pool = "cluster-a"`，path `/v1/chat/completions`，body `{"model":"sim-model",...,"max_tokens":8}`，超时 10s | pick 成功，返回 `x-gateway-destination-endpoint` 为 a0 的 `ip:port` |

## 预期结果

- 故障期间引擎版本保持 v1，服务不中断；恢复后版本自动追平为 v2。
- 追平后调度正常命中 a0。

## 清理

`defer e.Close()`：Kill epp/sim 进程并 Wait，关闭 mock API 与 gRPC 连接，`t.TempDir` 自动清理。
