# 场景说明：SC10 基于 vLLM 状态的差异化调度

所属场景编号：SC10；代码目录：`test/implementation/scenario-SC10-metrics-aware-scheduling`（包名 `sc10`）。

## 1. 背景与目的

验证 epp 的调度决策真正消费**后端实时指标**（需求分析 FR-D2 的指标驱动语义、G6 引擎复用的有效性）：同一 cluster 内两个后端上报不同的 vLLM 状态时，scorer 打分产生差异化调度——高负载后端被饿死、空闲后端独占流量；负载清除后调度回归均衡。

这是 SC01–SC09 未覆盖的关键路径：此前所有场景的 scorer 输入全为 0（所有端点同分，picker 随机选择），无法证明指标链路（sim /metrics → epp metrics-data-source → extractor → scorer）真实生效。

## 2. 后端状态控制

inference-sim 支持 **fake metrics**：

- 启动时加 `--fake-metrics '<json>'` 启用（未启用时 `/admin/config` 拒绝 fake-metrics 更新，报 "reporting real metrics"）；
- 运行时 `POST /admin/config`，body `{"fake-metrics": {"kv-cache-usage": 0.95, "waiting-requests": 8, "running-requests": 3}}`（固定值或 `"func:start:end:period"` 函数，如 `ramp:0:10:5s`）；
- 对应指标：`vllm:kv_cache_usage_perc`、`vllm:num_requests_waiting`、`vllm:num_requests_running`。

harness 封装：`StartSimWithFakeMetrics` / env 选项 `WithSimFakeMetrics`（按逻辑名启用）/ `SetSimFakeMetrics`（运行时更新）/ `SimMetricValue`（断言 sim 侧指标生效）。

## 3. 配置构造

每个 TC 用**单 scorer 配置**（`WithPickerConfigFn`），隔离被验证的指标：

- TC-01/03：`kv-cache-utilization-scorer`（消费 `kv-cache-usage`）
- TC-02：`queue-scorer`（消费 `waiting-requests`）

插件链：cluster-table-discovery + 单 scorer + max-score-picker + openai-parser。

## 4. TC 列表

| 编号 | 名称 | 断言要点 |
|---|---|---|
| TC-01 | KV-cache 偏好空闲端点 | 基线两后端均命中 → b0 设 `kv-cache-usage=0.95`（先断言 sim /metrics 已生效）→ 连续 10 次 pick 全部命中空闲端点 |
| TC-02 | 队列深度偏好空闲端点 | b0 设 `waiting-requests=8` → 连续 10 次 pick 全部命中空闲端点 |
| TC-03 | 负载清除回归均衡 | b0 从 0.95 清零 → 两后端重新都被命中 |

## 5. 依赖与就绪

同 SC01 §5。指标链路为异步采集（默认 50ms refresh），观察窗口 30s。
