# 场景说明：SC11 PrefixCacheAffinity 调度

所属场景编号：SC11；代码目录：`test/implementation/scenario-SC11-prefix-cache-affinity`（包名 `sc11`）。

## 1. 背景与目的

验证 **prefix-cache-scorer**（前缀缓存亲和调度）端到端生效：

- 请求首次被调度后，其 prompt 的前缀哈希由 `approx-prefix-cache` producer 的 `PreRequest` 记录到被选后端（**近似自主学习模式，不依赖 kv-cache 事件总线**）；
- 后续相同前缀的请求经 producer `Produce` 计算各后端最长前缀匹配，prefix scorer 按匹配长度打分，max-score-picker 稳定选中持有缓存的后端；
- 配置热加载换引擎后内存索引重置，亲和自动重新学习，服务不中断。

机制出处：`llm-d-router/pkg/epp/framework/plugins/scheduling/scorer/prefix/plugin.go`、`.../requestcontrol/dataproducer/approximateprefix/plugin.go`；上游配置样例 `llm-d-router/deploy/config/epp-estimate-prefix-cache-config.yaml`（`prefix-cache-scorer` 无需 producer 配置——`RegisterAsDefaultProducer` 默认接线）。

## 2. 配置构造

```
plugins: cluster-table-discovery + prefix-cache-scorer + max-score-picker
requestHandler: openai-parser
```

prompt 用固定的长文本（三个 pangram 重复组合，跨多个 hash block），保证 matchLen 足以拉开分差。

## 3. TC 列表

| 编号 | 名称 | 断言要点 |
|---|---|---|
| TC-01 | 亲和形成与收敛 | 同一长 prompt 连续 8 次 pick 全部命中同一后端（首次随机、后续由前缀匹配驱动）；收敛端点必须在 sim 集合内 |
| TC-02 | 不同前缀独立收敛 | 两个不同长 prompt 各自收敛到单一后端（亲和按前缀内容键控） |
| TC-03 | 热加载后亲和重学 | 插件重命名触发引擎热交换（索引随旧引擎销毁）→ 同一 prompt 在新引擎上重新收敛 |

## 4. 断言方式

`converged` 辅助函数：每轮以第一次 pick 结果为锚点，要求后续 burst-1 次全部一致；连续 burst 内一致才通过（纯随机命中同一后端的概率约 0.8%/burst，可忽略）。索引更新是异步的（`wg.Go`），轮询重试天然覆盖。

## 5. 依赖与就绪

同 SC01 §5。观察窗口 30s。
