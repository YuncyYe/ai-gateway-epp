# 场景说明：SC13 UtilizationFilter 调度

所属场景编号：SC13；代码目录：`test/implementation/scenario-SC13-utilization-filter`（包名 `sc13`）。

## 1. 背景与目的

验证 **utilization-filter** 的**硬过滤**语义，与 SC10 的 scorer 软偏好形成对照：

- 指标超阈值的端点被**移出候选集**（scorer 只是打低分，端点仍可能被选中）；
- 全部端点被过滤时**默认调度失败**（fail-closed，守门语义）；`fallbackOnEmpty: true` 时回落到未过滤候选继续服务。

机制出处：`llm-d-router/pkg/epp/framework/plugins/scheduling/filter/utilization/filter.go`。插件已在 cmd/epp 注册（此前仅进程内编译路径经过它，无行为断言）。

## 2. 配置构造

```
plugins: cluster-table-discovery + utilization-filter + max-score-picker（无 scorer）
filter 参数: conditions=[{metric: "kv-cache-utilization", maxValue: 0.9}], fallbackOnEmpty 按 TC
```

可用指标（上游常量）：`kv-cache-utilization`（0~1，服务端上报）、`waiting-queue`、`running-requests`（服务端上报）、`active-requests`（EPP 在飞计数）。本场景用 fake-metrics 控制 `kv-cache-usage`。

## 3. TC 列表

| 编号 | 名称 | 断言要点 |
|---|---|---|
| TC-01 | 过载端点被硬过滤 | 基线双端点命中 → b0 kv=0.95（>0.9 阈值）→ 连续 picks 全部命中空闲端点（硬移除，非低概率选中）→ 负载清零后双端点恢复 |
| TC-02 | 全过滤 fail-closed | 两端点都超阈值、fallbackOnEmpty=false → 调度失败、liveness 正常 → 一端恢复后调度恢复且只命中该端 |
| TC-03 | fallbackOnEmpty 回落 | 两端点都超阈值、fallbackOnEmpty=true → 请求仍被路由到全候选（超阈值端点也接受） |

## 4. 与 SC10 的对照

| | SC10 scorer（软偏好） | SC13 filter（硬过滤） |
|---|---|---|
| 超阈值端点 | 低分但仍可能被选中 | 移出候选集，不可能被选中 |
| 全部端点超阈值 | 仍调度（选分最高的） | 默认失败 / fallback 回落 |
| 典型用途 | 负载均衡优化 | 过载保护守门 |

## 5. 依赖与就绪

同 SC01 §5。fake-metrics 需启动时启用（`WithSimFakeMetrics`），指标采集异步（观察窗口 30s）。
