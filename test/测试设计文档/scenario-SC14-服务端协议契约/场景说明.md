# 场景说明：SC14 服务端协议契约（主端口 health + gRPC TLS）

所属场景编号：SC14；代码目录：`test/implementation/scenario-SC14-server-protocol`（包名 `sc14`）。

## 1. 背景与目的

验证两项 BFE 对接依赖的服务端协议能力（改动见 `cmd/epp/main.go`、`cmd/epp/config.go`）：

- **health 服务挂载到 ext-proc 主端口**：BFE failover 的健康检查朝 `EPPAddr`（数据端口）发 `grpc.health.v1.Check`，要求主端口直接给出就绪判活结果，而不是只能探独立 health 端口。就绪门控语义与 health 端口完全一致（assignment 首同步 + 全部 assigned cell ready）。
- **gRPC 服务端 TLS**：`-grpc-tls-cert`/`-grpc-tls-key` 同配生效（环境变量 `AI_GATEWAY_EPP_TLS_CERT`/`AI_GATEWAY_EPP_TLS_KEY`），ext-proc 与 health 两个 gRPC server 同时使用；缺省明文（兼容现有部署）；只配其一启动 fail-fast。

机制出处：`cmd/epp/main.go`（`serverOptions`、`healthpb.RegisterHealthServer` 双注册）、`cmd/epp/tls_test.go`（进程内单测，stub health）。本场景用**真实 epp 进程**补齐端到端契约验证。

## 2. TC 列表

| 编号 | 名称 | 断言要点 |
|---|---|---|
| TC-01 | 主端口 health 契约（明文） | InnerAPI 故障（`SetFail(true)`）期间，GRPCAddr 与 HealthAddr 的 health Check 均为 NOT_SERVING → 恢复并完成首同步后双端口均 SERVING → 主端口 liveness 常 SERVING → 主端口 ext-proc 调度不受影响（pick 命中 sim） |
| TC-02 | gRPC TLS 全链路 | 自签证书（SAN=127.0.0.1）启动 epp → TLS 双端口 health SERVING → **明文 ext-proc dial 与明文 health Check 均被拒** → TLS pick 命中 sim |
| TC-03 | TLS 配置 fail-fast | 只传 `-grpc-tls-cert` 不传 key → 进程 1s 内非零退出，日志含 "grpc-tls-cert and grpc-tls-key must be set together" |

## 3. harness 增量

- `common.WriteSelfSignedCert`：生成 ECDSA 自签证书（SAN=127.0.0.1），写 cert/key PEM 到临时目录并返回 `*x509.CertPool`（客户端校验用）。
- `common.CheckHealth` / `common.CheckHealthTLS`：对任意地址的单次 gRPC health Check（原 `EppEnv.checkHealth` 重构为其薄封装）。
- `common.PickEndpointTLS` / `PickEndpointWithHeadersCreds`：自定义 transport credentials 的 pick 变体。
- `Process.Stop`：调用方已自行 `Cmd.Wait()` 时（TC-03 断言启动失败）跳过重复 Wait，并始终关闭日志句柄（Windows TempDir 清理前提）。

## 4. 依赖与就绪

同 SC01 §5。TC-01 用 `SetFail(true)` 把就绪门控卡在 NOT_SERVING 阶段，消除"启动后就绪太快来不及断言"的时序不确定性；TC-02 不用 `NewEnv`（其 `WaitHealth` 是明文，对 TLS 进程会超时），改为手工组装环境并以 TLS 方式等待就绪。
