# ai-gateway-epp 集成测试场景总体说明

版本：v1.0（2026-09-06）。参照 `bfe/tests/integration` 测试规范。

## 1. 测试范围与形态

| 项 | 内容 |
|---|---|
| 被测组件（真实进程） | ai-gateway-epp（本仓库 `cmd/epp` 构建的二进制）、llm-d-inference-sim（vLLM 模拟器，OpenAI HTTP + /metrics） |
| Mock | ai-gateway-api InnerAPI（测试进程内 httptest，实现 `epp_data/config`（epp_config + assignment 全量视图，单 version 快照）与 `cluster_table` 两接口 + version 增量；退役的 assignment/report 路径保留为计数器，供"零上报"断言） |
| 扮演 | BFE——测试代码以 ext-proc gRPC 客户端连接 epp，发送带 `llm-d.ai/inference-pool` metadata 的 RequestHeaders，充当 BFE 的 `chooseBackendFromEPP` |
| 不在范围 | BFE 进程本身、ai-gateway-api 真实服务、K8s、真实 GPU 推理 |

## 2. 公共前置条件

1. 本机 Go 1.26+；`go build ./cmd/epp` 可用（harness 自动构建：每个测试包在进程独有临时目录构建私有副本，互不共享）。
2. inference-sim 二进制：`INFERENCE_SIM_BIN` 环境变量、 sibling checkout `../llm-d-inference-sim/bin/` 或 `test/.sim-bin/`；缺失时相关场景 `t.Skip`。
3. 全部监听 `127.0.0.1`，端口 `FindFreePort` 动态分配。

## 4. 场景-TC 对应关系

### SC01 单 cluster 调度闭环（scenario-SC01-single-cluster-scheduling）

| TC | 名称 | 目的 |
|---|---|---|
| TC-01 | 调度闭环 | 1 个 cluster、2 个 sim 后端：ext-proc 请求返回合法 `x-gateway-destination-endpoint`，真实 HTTP 请求打到该后端且响应正常 |
| TC-02 | demux 路由 | 2 个 cluster：不同 `inference-pool` metadata 路由到各自后端池 |
| TC-03 | 缺 pool metadata | 无 metadata 且未配 default-pool：返回错误，epp 进程存活 |
| TC-04 | 未知 pool | metadata 指向未分配 cluster：返回错误，其他 cluster 不受影响 |

### SC02 配置热加载（scenario-SC02-config-hot-reload）

| TC | 名称 | 目的 |
|---|---|---|
| TC-01 | 配置变更热生效 | epp_config 内容变化后无需重启完成引擎换入；`ai_epp_engine_current_version` 前移、调度正确 |
| TC-02 | 多 cluster 独立热加载 | 只改 cluster-b 配置：b 换入、a 版本不变 |
| TC-03 | 编译失败隔离 | 下发非法配置（未知插件类型）：`result="invalid"` 计数出现、旧引擎继续服务 |
| TC-04 | 配置回滚 | 配置改回上一版本后自动恢复旧引擎（同内容哈希），无需进程操作（FR-C5） |
| TC-05 | 生效时效 | 配置提交到引擎换入的耗时在 2×pollInterval 量级内（NFR-2，含 10x 调度抖动余量） |

### SC03 主备角色切换（scenario-SC03-assignment-role-switch）

| TC | 名称 | 目的 |
|---|---|---|
| TC-01 | 降备拒绝服务 | primary→standby：ext-proc 返回 Unavailable（"cell is not serving"），liveness 正常 |
| TC-02 | 提升恢复服务 | standby→primary：调度恢复（备 cell 热数据，开闸即服务）；断言零上报 |
| TC-03 | 摘除去 cell | assignment 移除 cluster：cell 销毁、其余 cluster 不受影响；断言零上报 |

### SC04 fail-static（scenario-SC04-innerapi-failure）

| TC | 名称 | 目的 |
|---|---|---|
| TC-01 | 故障期 fail-static | mock API 全部 500：调度基于最后同步状态继续、进程不退出 |
| TC-02 | 恢复后追平 | 故障窗口内下发的配置在恢复后自动生效（version 追平） |

### SC05 端点生命周期（scenario-SC05-endpoint-lifecycle）

| TC | 名称 | 目的 |
|---|---|---|
| TC-01 | 扩容 | cluster_table 增加 sim 后端：新端点被调度命中 |
| TC-02 | Weight=0 摘除 | 实例 Weight 改 0：不再被选中，流量落到剩余端点 |
| TC-03 | 全摘除与恢复 | 全部 Weight=0：调度失败、进程健康；恢复后服务自动恢复 |
| TC-04 | Weight 非比例语义 | 90/10 权重下两个后端仍都收到流量——Weight 只是注册/摘除开关（需求分析 §3.1.1） |

### SC06 流控（scenario-SC06-flow-control）

| TC | 名称 | 目的 |
|---|---|---|
| TC-01 | 流控生效并发突发 | flowControl 门开启（utilization-detector + maxRequests=1）：8 并发 pick 全部完成、路由正确（排队路径无死锁） |
| TC-02 | 非法流控配置 | saturationDetector 引用不存在：fail-static，旧引擎继续服务 |

> SC06 范围说明：EPP 流控作用于毫秒级调度周期，黑盒可稳定观测的是"配置生效/不死锁/非法配置隔离"；排队时延与公平性由上游基准测试覆盖，见场景文档。

### SC07 增量同步与拉取健康（scenario-SC07-incremental-sync）

| TC | 名称 | 目的 |
|---|---|---|
| TC-01 | 增量同步空转 | 稳态下 poller 持续携带 version 参数轮询、Data:null 不触发重建；版本推进但内容相同（hash 相同）时引擎不重编译（FR-D1） |
| TC-02 | 拉取健康指标 | 两个 poller（discovery / epp_data）的 last_sync_timestamp 存在；API 故障时 failures_total 递增、backoff_state=1；恢复后 backoff 清零（FR-O2） |

### SC08 cluster 数据驱动生命周期（scenario-SC08-cluster-lifecycle）

| TC | 名称 | 目的 |
|---|---|---|
| TC-01 | 新 cluster 动态纳入 | epp_data/config 与 cluster_table 同快照新增 cluster-b 后自动建 cell、发现端点、可调度，epp 无重启（FR-D4/FR-M3） |
| TC-02 | 未分配配置隔离 | epp_config 含未分配 cluster 的配置：不建 cell、零上报、不影响已分配 cluster（FR-C2） |

### SC09 双实例互备组（scenario-SC09-dual-instance-group）

| TC | 名称 | 目的 |
|---|---|---|
| TC-01 | 组内主备分工 | 2 实例组：全量视图中各 cluster 由本组主实例服务，对端备实例拒绝服务（FR-H1） |
| TC-02 | 互备切换 FailoverFlip | 全量视图角色翻转（A 主 B 备 → B 主 A 备）：备实例热接管服务、原主拒绝服务；双主在单 primary 全量视图下不可表达，failover 由 BFE 滞回驱动；断言零上报 |

### SC10 基于 vLLM 状态的差异化调度（scenario-SC10-metrics-aware-scheduling）

| TC | 名称 | 目的 |
|---|---|---|
| TC-01 | KV-cache 偏好空闲端点 | b0 上报 kv-cache-usage=0.95 → 连续 picks 全部命中空闲端点（指标链路真实生效的首次验证） |
| TC-02 | 队列深度偏好空闲端点 | b0 上报 waiting-requests=8 → 连续 picks 全部命中空闲端点 |
| TC-03 | 负载清除回归均衡 | fake metrics 清零后两后端重新都被调度 |

### SC11 PrefixCacheAffinity 调度（scenario-SC11-prefix-cache-affinity）

| TC | 名称 | 目的 |
|---|---|---|
| TC-01 | 亲和形成与收敛 | 相同长 prompt 连续 8 次 pick 命中同一后端（首次随机，后续由前缀匹配驱动） |
| TC-02 | 不同前缀独立收敛 | 两个不同 prompt 各自收敛（亲和按前缀内容键控） |
| TC-03 | 热加载后亲和重学 | 引擎热交换后索引重建，同一 prompt 自动重新收敛 |

### SC12 SessionAffinity 调度（scenario-SC12-session-affinity）

| TC | 名称 | 目的 |
|---|---|---|
| TC-01 | session 粘住 | 带 x-session-id 的请求连续 8 次命中同一端点；无 header 请求正常调度 |
| TC-02 | 多 session 独立 | 两个 session 各自粘住且互不干扰 |
| TC-03 | 绑定端点摘除迁移 | 绑定端点 Weight=0 后 session 迁移到存活端点并重新粘住 |

### SC13 UtilizationFilter 调度（scenario-SC13-utilization-filter）

| TC | 名称 | 目的 |
|---|---|---|
| TC-01 | 过载端点硬过滤 | kv-cache-utilization>0.9 的端点被移出候选集，流量全落空闲端点；负载恢复后回归 |
| TC-02 | 全过滤 fail-closed | 全部端点超阈值且 fallbackOnEmpty=false → 调度失败（守门语义），恢复后自动恢复 |
| TC-03 | fallbackOnEmpty 回落 | 全部端点超阈值但 fallbackOnEmpty=true → 回落到全候选继续服务 |

### SC14 服务端协议契约（scenario-SC14-server-protocol）

| TC | 名称 | 目的 |
|---|---|---|
| TC-01 | 主端口 health 契约 | ext-proc 数据端口同挂 health 服务：未就绪双端口 NOT_SERVING，就绪后双端口 SERVING，liveness 常 SERVING，数据面调度不受影响 |
| TC-02 | gRPC TLS 全链路 | 证书启动后明文 dial 被拒、TLS pick 与 health Check 正常，两端口同配 |
| TC-03 | TLS 配置 fail-fast | 只配 cert 不配 key → 进程秒级非零退出并输出明确错误 |
